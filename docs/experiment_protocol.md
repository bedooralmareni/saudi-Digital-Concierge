# Saudi Digital Concierge — M5/M6 preregistered protocol (v1.0)

**Status:** design frozen for implementation; no model results have been measured. This protocol defines the primary comparison **within each model**: single agent versus the four-role multi-agent system, using the same model, database, case, run ID, tools, and answer contract. Qwen-versus-OpenAI is a secondary descriptive comparison because the models differ. The manipulated factor is agent organization. Keep the retrieval implementation, access to records, answer schema, and scoring rules identical across conditions. If the multi-agent treatment has more calls or cost, report that as part of its measured trade-off.

## 1. Metrics and scoring decisions

Unit of evaluation is one **case × run × condition × model**. Save raw final JSON, normalized request, tool/agent trace, and source record IDs. Scores are computed by an external evaluator from the frozen gold; model-declared `status`, `constraint_results`, and `reason` are claims to verify, not the gold. Invalid JSON or missing required fields is a schema failure and scores zero on end-to-end success; retain any trace/cost/latency and flag unscorable component fields separately. A refusal or infrastructure error is a failure unless the case requires refusal to invent unsupported facts and the response actually provides the required explanation.

| Metric | Operational definition (case-level) | Missing / partial / no-match |
|---|---|---|
| **Hard-constraint satisfaction (HCS)**, primary | For each output option marked compliant, check all applicable hard constraints against its KB record: city, exact type/category, price inequality, rating scale, capacity, dates, flags and exclusion. `HCS = compliant selected options / all selected options`; if none selected on a positive-match case, score **0**. Also report binary `all_options_compliant`. | A NULL needed to prove a hard constraint is **unknown**, never satisfied. An unsupported option presented as compliant fails. For a case that correctly returns no options because the gold requires only no-match/coverage/clarification/unknown, HCS is **NA**; its success is captured by CC and E2E. If it wrongly proposes an option, HCS is **0**. |
| **Component completion (CC)** | For each requested component (hotel, restaurant, activity, event, information or clarification), award 1 only if the output supplies the required number of distinct admissible options **and** the required facts, or the exact prescribed no-result/unknown/clarification behavior. `CC = passed components / gold components`. For cases with no SQL components, treat the documented request-logic behavior as one component. | A mixed partial answer receives credit for completed parts only. For `X25`, one available distinct option plus an explicit shortfall counts as correct partial behavior; three fabricated/duplicate venues fail. No-result is scored by correct explanation, not by returning an arbitrary empty list. |
| **End-to-end case success (E2E)**, primary | 1 if **every** component passes, all proposed options comply, no unsupported factual claim appears, response language matches the case, and the output shape follows user intent (no unsolicited day plan for hotel-only questions). Otherwise 0. | `PARTIAL`, `NO_MATCH`, `COVERAGE_GAP`, `INSUFFICIENT_DATA`, `CLARIFY` can be **successful** if they match the gold behavior. E2E does not require a positive recommendation in such cases. |
| **Grounding / unsupported claim rate (UCR)** | `unsupported factual claims / factual claims checked`. Claims include entity, city, price, rating, dates, admission, opening hours, availability and trip cost. Check KB snapshots and gold; count one incorrect field as one unsupported claim. | Missing/unknown stated honestly is not an unsupported claim. If no factual claims are made, report UCR as **NA**, and separately score completeness/E2E. Human audit all nontrivial prose claims until extraction is validated. |
| **Schema validity (SV)** | 1 if final output parses as JSON and validates against `schema/response.schema.json`; else 0. Report separately from factual correctness. | `null`, `[]`, and status values are valid only when used consistently with documented semantics; structural validity alone never earns E2E. |
| **Tool/trajectory validity (TV)**, required trajectory-level metric | From the recorded trace, `TV = valid tool/agent actions / attempted tool/agent actions`. A valid action has a recognized name, parseable arguments, permitted recipient, no hard-constraint relaxation, and a recorded success/empty/error outcome; count invalid calls and repeated identical calls without new evidence as invalid. | No calls: `TV = NA` (not perfect); report a separate `unjustified_no_retrieval` flag when a matching factual case needed retrieval. Also report tool-error rate and attempted-call count. |
| **Cost and latency** | `wall_seconds` measured with monotonic clock across the entire case, including retries; OpenAI prompt/completion tokens and billed USD from actual usage and contemporaneous price schedule. Local Qwen: prompt/output tokens plus GPU seconds and estimated infrastructure cost if rate is documented. | Failure, timeouts, and partial answers stay in the denominator and contribute their actual calls, tokens and elapsed time. Do not present local GPU cost as OpenAI API billing. |

Use the **gold JSON** fields `expected_status`, `components[].mode`, `required_count`, `accepted_ids`, `distinct_option_groups`, `evidence`, and `behavior`. Return any admissible IDs; never restrict correctness to the workbook's first example. Count same-name/city options once (events also require same start/end to be duplicates). Record both a strict automated score and a blinded manual review of unsupported prose claims; review all disputed/ambiguous cases with a written decision and freeze adjudication rules before opening Final Test. Do not infer success from the model's own status alone.

**Status mapping:** `MATCH` → complete with all requested choices; `NO_MATCH` → no matching record in snapshot, no unsupported choices; `COVERAGE_GAP` → explain limited table coverage; `INSUFFICIENT_DATA` → identify NULL/unsupported field/live-availability gap; `CLARIFY` → ask the needed question; `PARTIAL` → provide supported components and name every unresolved one; `NOT_ONGOING` → compare the recorded event end with the fixed case date despite `is_active=1`. Map these gold values to response-schema statuses: `MATCH` and correctly explained `NOT_ONGOING` → `complete`, `NO_MATCH` → `no_match`, `COVERAGE_GAP` → `coverage_gap`, `INSUFFICIENT_DATA` → `insufficient_data`, `CLARIFY` → `needs_clarification` (or `conflicting` for contradictory bounds), and `PARTIAL` → `partial`. Never score the status string alone. A case-specific gold behavior overrides a generic label.

For success reporting, macro-average E2E over cases (each case has equal weight), then report HCS/CC with their denominators and E2E by Typical/Edge, Arabic/English, domain and status. Do not turn unknowns into zero ratings/prices or drop failure cases from denominators. Establish a single adjudication file for factual claims; the rubric calls for both end-to-end and component-level evaluation.

## 2. Evaluation protocol and leakage controls

The fixed set has 100 cases: Development 60 (42 Typical, 18 Edge), Validation 20 (14, 6), Final Test 20 (14, 6); each split is half Arabic and half English. It is bound to the DB SHA-256 in the scenario-package manifest. Related standalone/composite tasks were grouped in the same split. **Entity and template overlap remains**, and restaurants cover Riyadh only; report these as threats to validity.

1. **Development:** inspect prompts and gold, implement parsers, scoring, agents and error handling. Debug and change prompts/settings freely; log changes.
2. **Validation:** run candidate settings on the 20 cases and choose **one** configuration per model. Limit tuning to two documented revisions after the first validation run. Record all validation attempts and results; do not report the best trial as unbiased test performance.
3. **Freeze gate:** commit code/config/schema, model identity and resolved revision, prompt hashes, DB hash, scorer version, adjudication rules, prices used for cost, and run IDs before opening Final Test. Never tune on test outputs.
4. **Final Test:** run 20 cases × 3 runs × both architectures for each selected model. If infrastructure fails, rerun the **same** failed tuple and keep the original failure log; do not selectively replace low-quality outputs. If a semantic bug forces an implementation change, declare the test spent, version the protocol, and rerun the **whole** set for all conditions; disclose the change.

Runtime agent inputs include only the scenario's `scenario_id`, prompt, normalized request, shared instructions, and records returned by search tools. Never pass `gold.json`, SQL, accepted IDs, example evidence, status, expected behavior, evaluator notes, the answer-bearing spreadsheet, or whole evaluation-package README to an agent. Store gold under an evaluator-only path/process and invoke it **after** model output is finalized. In logs, retain hash and case ID so traces align without exposing gold. Validate the split artifact with `verify_ground_truth.py` before launch. Do not use Final Test samples as few-shot examples.

## 4. Multi-agent architecture

**Topology: centralized Supervisor with three specialists.** The Supervisor receives normalized request, creates only the needed subtasks and integrates the reply; specialists never talk to each other. Use the same underlying selected LLM model for all four roles within a model arm. Agents share the identical read-only KB tools; each specialist is restricted to its relevant subset. No flights or visas.

| Role | Tool access and trigger | Output / stop condition |
|---|---|---|
| Supervisor | Parse constraints, route by requested components and clarification status. No direct KB search in treatment. | Assemble the final response-schema object, deduplicate IDs, assess hard constraints and unknown costs. Stop after all required subtasks terminal or the global turn/time guard. |
| Hotel Agent | `search_hotels` only when lodging/capacity/recorded price requested. | Return matching hotel record IDs with exact evidence, `NO_MATCH`, `UNKNOWN`, or `TOOL_ERROR`; never infer availability/current price. |
| Attraction Agent | `search_places` for verified restaurants, or entertainment `entity_type` for attractions/activities; only when requested. | Return typed IDs and recorded ratings/category; NULL and missing Riyadh-only coverage stated explicitly. |
| Event Agent | `search_events` only when dated events requested. | Return event IDs and recorded start/end and family flag; distinguish starts-in-month versus overlap and do not infer live operation from `is_active` alone. |

If city/dates are essential and unresolved, Supervisor returns clarification without delegation. With conflicting hard bounds, return `conflicting`. Parallel specialists may run for independent components; result integration is deterministic by original request order: hotel, restaurant/activity, event. An absent specialist contributes no result and no invented itinerary slot. If one component fails, complete supported components and mark the whole response `partial`. Duplicate conflicting KB records remain separate evidence entries unless their name/city and relevant event dates identify a duplicate under the frozen scoring rule. Terminate after one documented broader search **only if it preserves all hard constraints**; otherwise return `no_match` or `coverage_gap`.

## 5. Inter-agent message protocol

Use JSON envelopes validated against `schema/agent_message.schema.json`. Every envelope has `schema_version`, `case_id`, `run_id`, `message_id`, `parent_message_id`, `sender`, `recipient`, `kind`, `component`, `constraints`, `outcome`, `record_ids`, `records`, `error_code`, `note`. `record_ids` must be exact KB IDs and the raw `records` array must contain only retrieved records, each with a fixed set of fields (nullable where absent). `kind=task` requests work; `kind=result` is terminal. Correlate the result to the task with `parent_message_id`; store monotonic timestamps and token/call usage in the **trace log**, not model-visible messages. Do not send gold or other specialists' private reasoning.

Outcomes: `MATCH` (verified records), `NO_MATCH` (successful empty search), `UNKNOWN` (missing field/coverage), `NEEDS_CLARIFICATION` (essential ambiguity), `TOOL_ERROR` (actual failure), `NOT_APPLICABLE` (component not requested). An empty successful search is **not** an error. On tool error retry once with identical hard constraints; if still failing, return `TOOL_ERROR`, continue other components and count trajectory failure. If a specialist requests clarification, Supervisor asks the user before further relevant search. Every tool call and agent handoff is traced with arguments and returned ID list, preserving prompts and failures for trajectory scoring.
